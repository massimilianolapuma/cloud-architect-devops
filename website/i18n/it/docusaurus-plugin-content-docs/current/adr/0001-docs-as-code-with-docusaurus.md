# ADR 0001: Documentazione come codice con Docusaurus, inglese canonico e italiano tradotto

## Contesto e problema

Queste linee guida sono lette da architetti che decidono, team di delivery che copiano e stakeholder che devono capire. Devono esistere in inglese e in italiano, le modifiche devono poter essere riviste, le pagine devono portare diagrammi di architettura, diagrammi Mermaid e diagrammi interattivi passo-passo, e i controlli automatici dovrebbero poter impedire la pubblicazione di una pagina rotta. Le linee guida coprono Azure, Google Cloud e le piattaforme on-prem. La domanda è dove vive il contenuto, quale strumento lo costruisce e lo pubblica e quale lingua è la fonte; questo repository costruisce già il proprio sito con uno degli strumenti candidati.

## Fattori decisionali

I pesi vengono dal confronto nel [capitolo che questo registro sostiene](../00-foundations/docs-as-code.mdx), sezione "Matrice pesata", e sommano a 100. Sono un giudizio dell'autore e attendono la conferma del decisore. Ogni fattore risale al brief o alla specifica del progetto; per revisione e audit, controlli automatici e continuità, la tabella dei criteri del capitolo dice dove l'autore applica un'esigenza dichiarata oltre la sua formulazione.

- Revisione e traccia di audit per ogni modifica (15).
- Inglese e italiano da un solo albero dei contenuti, con le traduzioni obsolete rilevate prima della pubblicazione (20).
- Controlli automatici che possono fermare la pubblicazione: link interni rotti e i controlli propri del progetto (20). La specifica del progetto richiede che `task verify`, che costruisce il sito in entrambe le lingue senza link rotti, passi prima che una fase sia chiusa; l'autore applica quel requisito alla pubblicazione.
- Componenti interattivi e diagrammi dentro le pagine: diagrammi passo-passo, Mermaid, export SVG dei sorgenti draw.io (15).
- I lettori che non scrivono contenuti possono leggere senza un ruolo sullo strumento di redazione; chi non usa git può contribuire (10).
- Continuità dello strumento e costo di portare fuori il contenuto (10).
- Funzionamento sull'infrastruttura propria dell'organizzazione e senza accesso a Internet (5).
- Linee guida versionate, cosa che il decisore ha definito il 2026-11-13 come cronologia git e tag, senza selettore di versione pubblicato (5).

## Opzioni considerate

- Docusaurus in git, inglese canonico, italiano tradotto e controllato da un gate di parità, pubblicato su GitHub Pages
- Hugo con il tema Docsy in git
- Antora in git
- Material for MkDocs in git
- Markdown renderizzato da GitHub (GitHub Enterprise Cloud), senza build del sito
- Wiki di Azure DevOps Services pubblicato come codice
- Confluence Cloud (piano Premium)
- SharePoint Online (pagine e raccolte documenti)
- SharePoint Server Subscription Edition

## Decisione

Opzione scelta: "Docusaurus in git, inglese canonico, italiano tradotto e controllato da un gate di parità, pubblicato su GitHub Pages", perché l'ha scelta il decisore: è già in uso in questo repository e, a giudizio del decisore, soddisfa le esigenze dichiarate. Le alternative sono state esaminate; sulle evidenze nessuna è risultata migliore.

Il giudizio che le esigenze dichiarate siano soddisfatte è la ragione del decisore. Ciò che le evidenze mostrano, esigenza per esigenza, è più ristretto:

- Revisione e traccia di audit: la traccia di audit viene da git su GitHub, non da Docusaurus; se una revisione della pull request possa essere resa obbligatoria non è nella ricerca, e oggi niente impone la revisione.
- Inglese e italiano: un solo albero dei contenuti con un percorso per locale è una funzionalità di Docusaurus. Le traduzioni obsolete non sono rilevate da Docusaurus; il controllo di parità di questo repository è scritto per segnalarle. I suoi test unitari per il caso della traduzione obsoleta sono passati il 2026-11-14 (`task test:tools`); il controllo non ha ancora segnalato una pagina obsoleta di questo sito.
- Controlli automatici: i link interni rotti fanno fallire una build di produzione per impostazione predefinita, e i link a file Markdown la fanno fallire per un'impostazione che questo repository usa; le ancore danno solo un avviso e gli URL esterni non sono documentati. I controlli di stato obbligatori che fermano un merge sono una funzionalità di GitHub, non di Docusaurus, e non sono ancora collegati.
- Componenti e diagrammi: i componenti React e Mermaid sono funzionalità di Docusaurus; le immagini SVG nelle pagine non hanno riscontri della ricerca.
- Raggiungibilità: soddisfatta in parte. I lettori di un sito GitHub Pages privato hanno bisogno dell'accesso in lettura al repository, che è un ruolo sullo strumento di redazione; altrimenti il sito è pubblico. Questa parte è stabilita, e il capitolo sull'hosting decide tra le due possibilità. Non è documentato se quei lettori abbiano bisogno anche di una licenza. Contribuire tramite git e pull request è disponibile; la ricerca non nomina nessun'altra via con un passaggio di revisione, e un editor proprio di Docusaurus non ha riscontri della ricerca.
- Continuità e uscita: soddisfatta in parte. La fine della linea 3.x è annunciata; il ciclo di vita di GitHub non ha riscontri. Due filoni di ricerca concludono che le pagine MDX con componenti andrebbero riscritte per essere spostate.
- Infrastruttura propria e offline: non soddisfatta così come è pubblicato, perché è GitHub Pages a servire il sito; non è stabilito se la build giri senza accesso a Internet.
- Versionato: soddisfatta dalla cronologia git e dai tag, non da Docusaurus.

Deciso dal decisore il 2026-11-13, e qui registrato come deciso:

- La forge dell'organizzazione è GitHub Enterprise Cloud. I controlli girano in locale e, dal 2026-11-14, a ogni pull request tramite un workflow GitHub Actions che riporta un esito senza fermare un merge; la loro applicazione sulla forge viene collegata nella fase di delivery.
- Il sito è pubblicato su GitHub Pages. L'accesso dei lettori, i limiti e le alternative su Azure, Google Cloud e on-prem sono rimandati a un successivo capitolo sull'hosting con un proprio registro della decisione.
- "Versionato" significa cronologia git e tag. Nessun selettore di versione pubblicato.
- Le lacune del controllo dei link sono documentate nel capitolo, e qualsiasi correzione è un follow-up separato. Le lacune sono: le ancore rotte danno solo un avviso, e gli URL esterni sono trattati come non controllati. La decisione indica gli URL esterni come non controllati; la ricerca non stabilisce se Docusaurus li controlli (vedi Conseguenze), e nessun test locale lo ha chiarito.
- La ricerca nel sito è lavoro successivo, non parte di questa decisione.
- Il capitolo che sostiene questo registro è una pagina MDX con un flusso interattivo.
- Finché non esiste la traduzione italiana di questo registro, `task i18n:check` lo segnala come mancante; questo è accettato per il pilota.

Che cosa dicono le evidenze sulle alternative. Il confronto del capitolo assegna il punteggio a un'opzione in base ai riscontri della ricerca e, in pochi casi dichiarati, in base a una definizione di ciò che l'opzione è (per esempio, un sito servito dal servizio di un fornitore non sta sull'infrastruttura propria dell'organizzazione); un livello fissato per definizione non è un fatto sul prodotto emerso dalla ricerca. La configurazione propria di questo repository non riceve punteggio: la riga Docusaurus è lo strumento pubblicato su GitHub Pages, senza il gate di parità di questo repository. Ogni criterio ha due sotto-esigenze, tranne il versionamento, che ne ha una; una sotto-esigenza che nessun riscontro definisce conserva il suo intervallo completo invece di una stima. Ogni generatore riceve il punteggio come pubblicato su GitHub Pages da GitHub Enterprise Cloud, il contesto deciso. Ogni opzione ha quindi un minimo (ogni punto aperto a suo sfavore) e un massimo (ogni punto aperto a suo favore), con i pesi del capitolo.

Un'opzione è totalizzata solo quando la sua copertura è superiore a metà del peso. La copertura è il peso dei criteri su cui un riscontro o una definizione restringe il punteggio dell'opzione al di sotto dell'intervallo completo. Sette delle nove opzioni passano, con una copertura di 80 o più. Confluence Cloud e SharePoint Server Subscription Edition no: per nessuno dei due un riscontro fissa un livello sulle due lingue, sui controlli automatici o su componenti e diagrammi, che portano 55 dei 100 punti, quindi la loro copertura è 45 e non hanno totali. La soglia è un giudizio dell'autore.

| Opzione | Copertura | Minimo | Massimo |
|---|---|---|---|
| Docusaurus, pubblicato su GitHub Pages | 100 | 360 | 425 |
| Hugo con Docsy, pubblicato su GitHub Pages | 100 | 305 | 475 |
| Antora, pubblicato su GitHub Pages | 80 | 270 | 475 |
| Material for MkDocs, pubblicato su GitHub Pages | 100 | 320 | 445 |
| Markdown renderizzato da GitHub | 80 | 280 | 460 |
| Wiki di Azure DevOps Services pubblicato come codice | 80 | 305 | 410 |
| SharePoint Online | 85 | 250 | 470 |
| Confluence Cloud (Premium) | 45 | non totalizzato | non totalizzato |
| SharePoint Server Subscription Edition | 45 | non totalizzato | non totalizzato |

- L'intervallo di ciascuna delle sei alternative totalizzate si sovrappone all'intervallo di Docusaurus. Nel confronto criterio per criterio con Docusaurus, la differenza totale di ciascuna delle sei va da sotto zero a sopra zero, sia con i pesi del capitolo sia con pesi uguali: su queste evidenze nessuna delle sei risulta migliore di Docusaurus, e nessuna risulta peggiore.
- Per Hugo con Docsy, Antora, Material for MkDocs e Markdown renderizzato da GitHub questo vale per qualsiasi scelta dei pesi: su ogni criterio la differenza rispetto a Docusaurus include lo zero. Su alcuni criteri può andare in una sola direzione: Docusaurus non è più basso di Hugo con Docsy, Antora o Markdown renderizzato da GitHub sui controlli automatici, non è più basso di Markdown renderizzato da GitHub sulla raggiungibilità e sull'infrastruttura propria, e non è più alto di esso sulla continuità. Per le altre due, alcuni pesi le separerebbero. Le direzioni stabilite sono: il wiki di Azure DevOps è più basso di Docusaurus sui controlli automatici e su componenti e diagrammi; SharePoint Online è più basso sul versionamento. Sulla raggiungibilità SharePoint Online non è più basso di Docusaurus, e se sia più alto è aperto.
- Le due opzioni senza totali possono essere confrontate con Docusaurus solo sui criteri in cui hanno riscontri. Confluence Cloud è più alto sulla raggiungibilità, un risultato che poggia su un articolo di Atlassian segnalato come da correggere, e più basso sul versionamento. SharePoint Server Subscription Edition è più alto sull'infrastruttura propria e più basso sul versionamento. Sulle due lingue, sui controlli automatici e su componenti e diagrammi non si può dire nulla di nessuno dei due.
- Sulla raggiungibilità, il punteggio di Docusaurus è stabilito nella sua prima metà: un sito GitHub Pages privato è leggibile solo con l'accesso in lettura al repository, che è un ruolo sullo strumento di redazione, e altrimenti il sito è pubblico. Non è documentato se tali lettori abbiano bisogno anche di una licenza, e ciò non cambia il punteggio.
- Se la conclusione dei filoni di ricerca secondo cui le pagine MDX andrebbero riscritte ricevesse punteggio, il massimo di Docusaurus scenderebbe da 425 a 415; il confronto non le assegna un punteggio, perché è un'analisi dei filoni, non un riscontro.
- I punti aperti di Docusaurus stesso sono: se una revisione della pull request possa essere resa obbligatoria su GitHub, le immagini SVG nelle pagine (nessun riscontro della ricerca), se Docusaurus offra un editing proprio per chi non usa git, il ciclo di vita di GitHub Enterprise Cloud e di GitHub Pages (la fine della linea 3.x è annunciata), se un altro strumento possa leggere le sue pagine MDX così come sono, e la build senza accesso a Internet. I punti aperti di ciascuna alternativa sono elencati più sotto in Pro e contro delle opzioni e, cella per cella, nel capitolo.
- Il costo di ricostruire il sito esistente su un altro strumento non è misurato.

L'inglese è l'unica fonte. I file italiani rispecchiano i percorsi inglesi; ciascuno porta un hash del file inglese da cui è stato tradotto, e il controllo di questo repository segnala un file italiano mancante, orfano o obsoleto. Questo segue la pratica della documentazione di Microsoft: la documentazione di PowerShell dice ["Tutte le traduzioni partono prima dal contenuto in inglese"](https://learn.microsoft.com/powershell/scripting/community/contributing/get-started-writing?view=powershell-7.6), e la guida per i contributori di Dynamics 365 accetta pull request [solo sui file sorgente in inglese](https://learn.microsoft.com/dynamics365/fin-ops-core/dev-itpro/help/contributor-guide).

### Conseguenze

Dei costi qui sotto, quattro poggiano sulle decisioni del decisore del 2026-11-13: il fallimento di `task i18n:check` (accettato per il pilota), il controllo parziale dei link (documentato nel capitolo, correzione successiva), i controlli che per ora niente sulla forge impone, e la ricerca nel sito come lavoro successivo. L'accesso dei lettori al sito, i limiti pubblicati di GitHub Pages e l'infrastruttura propria su GitHub Pages non sono accettati qui: sono punti aperti per il capitolo sull'hosting. Ogni altro costo è una conseguenza che il decisore accetta accettando questo registro.

- Positivo, perché le linee guida vivono in git, quindi le modifiche possono essere riviste e tracciate come il codice. Google riferisce che portare la documentazione del proprio wiki sotto controllo del codice sorgente e revisione del codice è ciò che l'ha fatta migliorare ([Software Engineering at Google, capitolo 10](https://abseil.io/resources/swe-book/html/ch10.html)), e l'Azure Well-Architected Framework chiede di ["Usare un controllo del codice sorgente unificato per tutto il codice, gli script, i template di deployment, le definizioni delle pipeline e la relativa documentazione"](https://learn.microsoft.com/azure/well-architected/operational-excellence/principles). Oggi niente impone la revisione (vedi sotto).
- Positivo, perché entrambe le lingue vengono da un solo albero: i file tradotti stanno sotto `website/i18n/`, e ogni locale è costruito come una propria applicazione a pagina singola con un proprio percorso ([introduzione a i18n](https://docusaurus.io/docs/i18n/introduction), [tutorial i18n](https://docusaurus.io/docs/i18n/tutorial)).
- Positivo, perché le pagine possono renderizzare componenti React tramite MDX ([MDX e React](https://docusaurus.io/docs/markdown-features/react)) e Mermaid tramite il tema ufficiale ([Diagrammi](https://docusaurus.io/docs/markdown-features/diagrams)).
- Positivo, perché una build di produzione fallisce sui link interni rotti per impostazione predefinita, e i link a file Markdown possono essere fatti fallire con un'impostazione, che questo repository usa ([docusaurus.config.js](https://docusaurus.io/docs/api/docusaurus-config)).
- Positivo, perché l'output è fatto di semplici file statici: ["L'unica responsabilità di Docusaurus è costruire il sito ed emettere file statici in `build`"](https://docusaurus.io/docs/deployment).
- Positivo, perché Docusaurus ha [licenza MIT](https://github.com/facebook/docusaurus/blob/main/LICENSE).
- Negativo, perché Docusaurus non rileva le traduzioni obsolete: ["purtroppo non abbiamo un buon modo per aiutarti a farlo"](https://docusaurus.io/docs/i18n/git). Il controllo di parità è codice proprio di questo progetto, da possedere e da testare. Copre le pagine Markdown e MDX; il testo italiano dentro i file dei flussi interattivi è controllato solo per la presenza, non per l'aggiornamento.
- Negativo, perché il testo della cornice del sito è fuori da quel controllo. Docusaurus ha per esso file di traduzione JSON, che `docusaurus write-translations` scrive (["Scrive i file di traduzione JSON che dovrai tradurre"](https://docusaurus.io/docs/cli)); questo repository non ne ha sotto `website/i18n/it/`, il controllo di parità non legge file JSON, e nella build locale del 2026-11-14 l'etichetta di navigazione "Guidelines" è in inglese nelle pagine italiane (registrato nello Stato di verifica del capitolo).
- Negativo, perché una pagina senza file italiano viene comunque costruita sotto `/it/` con il suo testo inglese: nella build locale del 2026-11-14 è stato così per questo registro e per il capitolo, prima che l'uno o l'altro avessero un file italiano (registrato nello Stato di verifica del capitolo). `task i18n:check` è il controllo che segnala un file italiano mancante.
- Negativo, perché `task i18n:check` fallisce finché questo registro non ha una traduzione italiana; il 2026-11-14 ha segnalato come mancanti questo registro e il capitolo. Il decisore lo ha accettato per il pilota.
- Negativo, perché le pagine che incorporano componenti sono MDX, dove ["tutto ciò che sembra HTML è in realtà JSX"](https://docusaurus.io/docs/markdown-features/react), un formato che la documentazione di Docusaurus definisce ["piuttosto rigido"](https://docusaurus.io/docs/markdown-features/react). Due filoni di ricerca concludono, nella loro analisi dei compromessi, che le pagine con componenti interattivi non sono portabili su Hugo con Docsy, MkDocs o Antora senza riscrittura; nessun riscontro della ricerca nomina uno strumento che le legga così come sono. Il confronto non assegna un punteggio a quell'analisi, perché non è un riscontro.
- Negativo, perché il controllo dei link è parziale: le ancore rotte danno solo un avviso per impostazione predefinita ([docusaurus.config.js](https://docusaurus.io/docs/api/docusaurus-config)) e questo repository non cambia quell'impostazione. La pagina di configurazione di Docusaurus non dice se gli URL esterni siano controllati; l'unica affermazione trovata è un [commento di un maintainer del 2020](https://github.com/facebook/docusaurus/issues/3303) secondo cui non lo sono, e una pull request di terze parti afferma il contrario (non verificato). Il capitolo documenta queste lacune; le correzioni sono un follow-up separato.
- Negativo, perché oggi niente sulla forge impone i controlli: girano su una postazione di lavoro e, dal 2026-11-14, a ogni pull request tramite `.github/workflows/verify.yml`, che riporta un esito ma non ferma un merge, perché non è configurato alcun controllo di stato obbligatorio. Il decisore lo ha deciso per ora; l'applicazione sulla forge viene collegata nella fase di delivery.
- Negativo, perché su GitHub la protezione dei branch [non si applica agli amministratori del repository per impostazione predefinita](https://docs.github.com/en/repositories/configuring-branches-and-merges-in-your-repository/managing-protected-branches/about-protected-branches). Nessuna decisione copre questo punto; è accettato accettando questo registro.
- Negativo, perché la ricerca non ha coperto se una revisione della pull request possa essere resa obbligatoria su GitHub. Nessuna decisione copre questo punto; è accettato accettando questo registro.
- Negativo, per via di chi può leggere il sito su GitHub Pages. Secondo la [pagina di GitHub sui siti pubblicati in privato](https://docs.github.com/en/enterprise-cloud@latest/pages/getting-started-with-github-pages/about-privately-published-github-pages-sites), un sito pubblicato in privato può essere letto solo da chi ha accesso in lettura al repository; altrimenti il sito è pubblico su Internet. Con Enterprise Managed Users un sito può essere solo privato ed è accessibile solo ai membri dell'enterprise; non è documentato se un membro senza accesso in lettura al repository possa aprirlo. Senza Enterprise Managed Users, gli stakeholder che non hanno un ruolo sul repository possono quindi leggere il sito solo se è pubblico. Nelle pagine di Pages lette non è documentato se quei lettori consumino una licenza a pagamento; su GitHub Enterprise Cloud, i membri dell'organizzazione e i collaboratori esterni su repository privati o interni [consumano una licenza](https://docs.github.com/en/enterprise-cloud@latest/billing/reference/github-license-users). Questa limitazione non è accettata da questo registro: è un punto aperto per il capitolo sull'hosting, che decide tra pubblicazione privata e pubblica.
- Negativo, perché, così come è pubblicato su GitHub Pages, il sito è servito dal servizio di GitHub, quindi il confronto gli assegna il punteggio, per definizione e non in base a un fatto emerso dalla ricerca, come non sull'infrastruttura propria dell'organizzazione e non leggibile senza accesso a Internet. L'[output della build è fatto di file statici](https://docusaurus.io/docs/deployment) che un altro host potrebbe servire; il capitolo sull'hosting lo valuta.
- Negativo, perché lasciare GitHub Enterprise Cloud ha un costo per un sito privato: la pubblicazione privata esiste solo con Enterprise Cloud, e dopo che un'organizzazione lo lascia, i suoi siti privati esistenti restano privati, non possono essere resi pubblici, e non si può creare alcun nuovo sito privato ([pagina di GitHub sui siti pubblicati in privato](https://docs.github.com/en/enterprise-cloud@latest/pages/getting-started-with-github-pages/about-privately-published-github-pages-sites)). Nessuna decisione copre questo punto; è accettato accettando questo registro.
- Negativo, perché la [panoramica delle funzionalità di GitHub Enterprise Cloud con data residency](https://docs.github.com/en/enterprise-cloud@latest/admin/data-residency/feature-overview-for-github-enterprise-cloud-with-data-residency) di GitHub non menziona GitHub Pages, né come disponibile né come non disponibile, quindi non è stabilito se l'host deciso possa essere usato lì. Nessuna decisione copre questo punto; è accettato accettando questo registro.
- Negativo, perché le pagine di GitHub Pages lette non descrivono alcun deployment di anteprima per pull request, e non è stato trovato alcun annuncio ufficiale al riguardo: per come è documentato, un revisore vede la modifica renderizzata prima del merge solo costruendo il branch in locale. Le action di terze parti per le anteprime sono note solo da fonti secondarie. Nessuna decisione copre questo punto; è accettato accettando questo registro.
- Negativo, perché GitHub Pages ha [limiti pubblicati](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits): un sito non più grande di 1 GB, un limite flessibile di banda di 100 GB al mese, e deployment che vanno in timeout dopo 10 minuti. Se contino per questo sito è un punto aperto per il capitolo sull'hosting.
- Negativo, perché il sito non è ancora configurato per GitHub Pages: `website/docusaurus.config.ts` imposta un `url` segnaposto e non imposta `trailingSlash`, che la [guida al deployment di Docusaurus](https://docusaurus.io/docs/deployment) raccomanda di impostare in modo esplicito su GitHub Pages. È lavoro della fase di delivery.
- Negativo, perché c'è una migrazione in vista: Docusaurus dice che la 3.10 ["sarà l'ultima release della linea v3.x, e ti aiuta a prepararti a Docusaurus v4"](https://docusaurus.io/blog); la ricerca non dà una data per la v4 e non dice per quanto tempo la 3.10 riceva correzioni. Il minimo documentato, Node.js 20, è [a fine vita](https://nodejs.org/en/about/previous-releases), e `website/package.json` ammette ancora Node 20.
- Negativo, perché installare le dipendenze senza accesso a Internet richiede uno store dei pacchetti già riempito: con `--offline`, [pnpm usa solo i pacchetti già presenti nello store](https://pnpm.io/cli/install). Non è stabilito se la build giri poi senza accesso a Internet, né se il sito costruito faccia richieste a Internet quando viene letto.
- Negativo, perché contribuire tramite git e pull request è disponibile, ma la ricerca non nomina nessun'altra via di contribuzione con un passaggio di revisione (Docusaurus nomina workflow di traduzione tramite software SaaS, senza che sia descritto un passaggio di revisione, e un editor proprio non ha riscontri), e Docusaurus indica il proprio workflow di traduzione con git come ["Difficile per chi non è sviluppatore"](https://docusaurus.io/docs/i18n/git).
- Negativo, perché le etichette dei diagrammi restano in inglese in entrambe le lingue: un solo SVG esportato serve entrambi i locale, e Google osserva che il testo dentro le figure ["aumenta i costi di localizzazione se le figure vengono localizzate"](https://developers.google.com/style/images) e "danneggia l'accessibilità e la ricercabilità"; il secondo costo vale per questi diagrammi così come sono.
- Negativo, perché un solo capitolo serve tre pubblici. Google consiglia di tenere i documenti per i clienti separati dai documenti per i fornitori ["Per quanto possibile"](https://abseil.io/resources/swe-book/html/ch10.html); un filone di ricerca, nella propria analisi, definisce una sola fonte per tre pubblici coerente con quell'indicazione ma più restrittiva. L'approccio si affida al fatto che ogni capitolo abbia le stesse sezioni fisse, e nessuna evidenza dimostra che bastino.
- Negativo, perché il sito non ha una ricerca finché non sarà fatto il successivo lavoro sulla ricerca nel sito.

### Conferma

Ci si aspetta che ciascuno di questi task passi prima che una modifica sia pubblicata. Oggi girano su una postazione di lavoro e, dal 2026-11-14, a ogni pull request (`.github/workflows/verify.yml`); niente sulla forge li impone, e la loro applicazione viene collegata nella fase di delivery.

- `task content:lint`: ogni capitolo e ogni registro della decisione ha il suo frontmatter e le sue sezioni obbligatorie.
- `task i18n:check`: nessuna pagina italiana è mancante, orfana o obsoleta rispetto alla sua fonte inglese.
- `task diagrams:check`: ogni sorgente draw.io ha un export SVG aggiornato e ogni SVG ha un sorgente.
- `task flows:check`: ogni file di flusso interattivo è ben formato e ha il testo in inglese e in italiano.
- `task site:build`: entrambi i locale vengono costruiti, con `onBrokenLinks` e `markdown.hooks.onBrokenMarkdownLinks` impostati a `throw` in `website/docusaurus.config.ts`.

`task verify` li esegue insieme a `doctor`, `test:tools` e `agentic:lint`, e `Taskfile.yml` lo descrive come un task che si ferma al primo fallimento. Il 2026-11-14 `task i18n:check` è fallito perché questo registro e il capitolo non avevano ancora una traduzione italiana, quindi `task verify` non poteva passare finché le traduzioni non fossero esistite; una volta esistite, `task verify` è stato eseguito lo stesso giorno ed è uscito con 0 (registrato nello Stato di verifica del capitolo). L'esecuzione degli stessi task come controlli obbligatori su GitHub viene collegata nella fase di delivery.

## Pro e contro delle opzioni

### Docusaurus in git, inglese canonico, italiano tradotto e controllato da un gate di parità, pubblicato su GitHub Pages

Il confronto assegna il punteggio allo strumento pubblicato su GitHub Pages; il gate di parità è codice proprio di questo repository e non riceve punteggio.

- Positivo, perché due lingue da un solo albero, componenti React nelle pagine, Mermaid e una build che fallisce sui link interni rotti sono funzionalità documentate (vedi Conseguenze).
- Positivo, perché il sito, il componente passo-passo e i task di controllo esistono già in questo repository, e il sito viene costruito in entrambi i locale.
- Negativo, perché lo strumento non rileva le traduzioni obsolete, le ancore rotte danno solo un avviso per impostazione predefinita, e il controllo dei link esterni non è documentato.
- Negativo, perché due filoni di ricerca concludono che le pagine MDX con componenti andrebbero riscritte per passare a un altro strumento (una loro analisi, non un riscontro), la 3.10 è l'ultima release della linea 3.x, i lettori di un sito GitHub Pages privato hanno bisogno dell'accesso in lettura al repository, e, così come è pubblicato su GitHub Pages, il sito non sta sull'infrastruttura propria dell'organizzazione (per definizione).
- Aperto: le revisioni obbligatorie delle pull request su GitHub, le immagini SVG (nessun riscontro della ricerca), un editing proprio per chi non usa git, il ciclo di vita di GitHub Enterprise Cloud e di GitHub Pages, se un altro strumento possa leggere le sue pagine MDX così come sono, la build senza accesso a Internet.

### Hugo con il tema Docsy in git

- Positivo, perché ogni lingua ha la propria radice dei contenuti e il [menu delle lingue](https://www.docsy.dev/docs/language/) porta alla versione tradotta della pagina corrente o alla home page di quella lingua; Hugo collega le traduzioni [per percorso, per directory dei contenuti o per una chiave condivisa](https://gohugo.io/content-management/multilingual/).
- Positivo, perché Docsy renderizza [Mermaid da un blocco di codice](https://www.docsy.dev/docs/content/diagrams-and-formulae/) e può aggiungere un pulsante di modifica alle immagini SVG che incorporano il proprio sorgente draw.io (un aiuto alla modifica, non un renderer di file draw.io), e i link scritti con `ref` o `relref` fanno fallire la build per impostazione predefinita ([configurazione](https://gohugo.io/configuration/all/)).
- Positivo, perché Hugo è [Apache-2.0](https://gohugo.io/about/license/) con release datate da luglio a ottobre (il fetcher della ricerca ha dedotto l'anno 2026) nella sua [pagina delle release](https://github.com/gohugoio/hugo/releases), e Docsy è un [progetto della Linux Foundation](https://github.com/google/docsy) con licenza Apache-2.0.
- Negativo, perché il [render hook incorporato per i link](https://gohugo.io/render-hooks/links/) di Hugo non segnala una destinazione che non riesce a risolvere; non è stabilito se un semplice link Markdown rotto possa far fallire una build di Hugo.
- Aperto: un indirizzo separato per lingua (le pagine sulle lingue non lo affermano), l'incorporamento di un componente React in una pagina Markdown (la pagina di [`js.Build`](https://gohugo.io/functions/js/build/) impacchetta codice React ma non documenta il suo incorporamento in una pagina), le immagini SVG nelle pagine, il rilevamento delle traduzioni obsolete, un editor proprio per chi non usa git, la manutenzione di Docsy (nessuna release datata di Docsy nella ricerca), il ciclo di vita di GitHub Enterprise Cloud e di GitHub Pages, la build senza accesso a Internet.

### Antora in git

- Positivo, perché le versioni dei contenuti vengono dai branch o dai tag di git, con il nome della versione preso dalla chiave `version` ([metodi di versionamento](https://docs.antora.org/antora/latest/content-source-versioning-methods/)), e Antora 3 è indicato come attivo, con la fine vita ancora da fissare, nel suo [calendario delle release](https://docs.antora.org/antora/latest/project/release-schedule/), che dice anche che le date sono stime e che una linea è tipicamente supportata per un anno dopo la disponibilità generale.
- Positivo, perché un riferimento incrociato non risolto è [registrato nel log come errore](https://docs.antora.org/antora/latest/playbook/runtime-log-format/) e un [livello di fallimento](https://docs.antora.org/antora/latest/playbook/runtime-log-failure-level/) fa uscire la build con un codice diverso da zero per i messaggi a quel livello o superiori (predefinito `fatal`).
- Negativo, perché AsciiDoc è il suo linguaggio dei contenuti e la [documentazione](https://docs.antora.org/antora/latest/) non elenca Markdown tra gli input; non è stabilito se non possa elaborare affatto Markdown.
- Negativo, perché la via documentata verso Mermaid è l'[estensione asciidoctor-kroki](https://docs.asciidoctor.org/kroki-extension/latest/) con un server Kroki, e le versioni JavaScript 1.0 e successive di quell'estensione sono riportate come non ancora compatibili con Antora.
- Aperto: la localizzazione (nessuna pagina ufficiale di Antora trovata; Fedora ha riferito di [costruire un sito separato per lingua](https://communityblog.fedoraproject.org/fedora-docs-translations-fad-report/), una fonte secondaria), i componenti interattivi, le immagini SVG, un editor proprio per chi non usa git, il ciclo di vita di GitHub Enterprise Cloud e di GitHub Pages, la build senza accesso a Internet.

### Material for MkDocs in git

- Positivo, perché i problemi dei link diventano errori con [`mkdocs build --strict`](https://www.mkdocs.org/user-guide/configuration/) (i controlli sulle ancore hanno come predefinito `info`), Mermaid è [supportato nativamente](https://squidfunk.github.io/mkdocs-material/reference/diagrams/), e un [plugin offline](https://squidfunk.github.io/mkdocs-material/plugins/offline/) fa funzionare un sito costruito dal file system; questo riguarda una copia letta dal file system, non il sito servito da GitHub Pages.
- Negativo, perché ["supporta solo l'impostazione di una lingua canonica per l'intero progetto"](https://squidfunk.github.io/mkdocs-material/setup/changing-the-language/): una seconda lingua è un secondo progetto.
- Negativo, perché è [in modalità di manutenzione](https://squidfunk.github.io/mkdocs-material/blog/2025/11/05/zensical/): lo sviluppo di nuove funzionalità è terminato e le correzioni critiche arrivano fino al 5 maggio 2027. Lo stesso post definisce MkDocs stesso non mantenuto da agosto 2024, e lega anche la data di maggio 2027 alla fine della "manutenzione upstream" senza dire che cosa significhi upstream. Il suo successore Zensical può costruire i progetti Material supportati dallo stesso `mkdocs.yml`.
- Aperto: i componenti interattivi, le immagini SVG, il rilevamento delle traduzioni obsolete, un editor proprio per chi non usa git, il ciclo di vita di GitHub Enterprise Cloud e di GitHub Pages, la build senza accesso a Internet.

### Markdown renderizzato da GitHub (GitHub Enterprise Cloud)

- Positivo, perché è semplice Markdown che GitHub renderizza, [Mermaid incluso](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/creating-diagrams), senza niente da costruire o da ospitare, e anche GitLab renderizza [documenti Markdown e Mermaid](https://docs.gitlab.com/user/markdown/).
- Negativo, perché i lettori di un repository privato o interno hanno bisogno di un ruolo su di esso, e su GitHub Enterprise Cloud i membri dell'organizzazione e i collaboratori esterni su repository privati o interni [consumano una licenza](https://docs.github.com/en/enterprise-cloud@latest/billing/reference/github-license-users); un repository pubblico è aperto a tutti.
- Negativo, perché la vista renderizzata è il servizio di GitHub, quindi il confronto le assegna il punteggio, per definizione e non in base a un fatto emerso dalla ricerca, come non sull'infrastruttura propria dell'organizzazione e non leggibile senza accesso a Internet; ogni clone del repository contiene comunque i file Markdown.
- Aperto: il controllo dei link da parte di GitHub stesso, i componenti interattivi, le immagini SVG, le due lingue e qualsiasi instradamento per lingua, il ciclo di vita di GitHub Enterprise Cloud.

### Wiki di Azure DevOps Services pubblicato come codice

- Positivo, perché il contenuto è Markdown in un repository git e la revisione viene dalle branch policy sul branch pubblicato ([pubblicare un repository come wiki](https://learn.microsoft.com/azure/devops/project/wiki/publish-repo-to-wiki?view=azure-devops)), compresi un [numero minimo di revisori e una build validation obbligatoria](https://learn.microsoft.com/azure/devops/repos/git/branch-policies-overview?view=azure-devops).
- Negativo, perché niente gira tra il merge e la pubblicazione (["Non sono coinvolti altri workflow"](https://learn.microsoft.com/azure/devops/project/wiki/publish-repo-to-wiki?view=azure-devops)), e il controllo dei link gira solo quando una pagina viene spostata nell'interfaccia del wiki ([aggiungere e modificare pagine wiki](https://learn.microsoft.com/azure/devops/project/wiki/add-edit-wiki?view=azure-devops)).
- Negativo, perché ["Markdown in Azure DevOps non supporta JavaScript né iframe"](https://learn.microsoft.com/azure/devops/project/wiki/markdown-guidance?view=azure-devops); il supporto di Mermaid è limitato, con la sintassi `flowchart` tra quelle non supportate, e SVG non è tra i formati immagine elencati per gli allegati.
- Negativo, perché nei progetti privati gli utenti Stakeholder gratuiti [non possono leggere i code wiki pubblicati](https://learn.microsoft.com/azure/devops/project/wiki/manage-readme-wiki-permissions?view=azure-devops), e i progetti pubblici sono [in via di ritiro](https://learn.microsoft.com/azure/devops/organizations/projects/public-projects-retirement?view=azure-devops), con l'accesso anonimo disabilitato nel 2027.
- Aperto: il rilevamento delle traduzioni obsolete, qualsiasi funzionalità multilingue, le immagini SVG inline.

### Confluence Cloud (piano Premium)

Esaminato e non totalizzato: nessun riscontro della ricerca fissa un livello per questa opzione sulle due lingue, sui controlli automatici o su componenti e diagrammi.

- Positivo, perché le pagine si modificano nel browser, la [cronologia della pagina](https://support.atlassian.com/confluence-cloud/docs/use-confluence-for-technical-documentation/) mostra ogni versione con il suo autore, e le [approvazioni](https://support.atlassian.com/confluence-cloud/docs/request-and-manage-approvals-in-confluence/) esistono nei piani Premium ed Enterprise; un amministratore dello spazio può richiedere l'approvazione prima che le nuove pagine vadano online (le modifiche a pagine esistenti non sono trattate).
- Negativo, perché i suoi [formati di esportazione](https://support.atlassian.com/confluence-cloud/docs/export-content-to-word-pdf-html-and-xml/) sono Word, PDF, CSV, HTML e XML; Markdown non è menzionato.
- Positivo, perché nel piano Premium i lettori possono avere un accesso anonimo limitato da una allowlist di IP, senza licenza, e gli ospiti possono restare non fatturabili, secondo l'[articolo della knowledge base sui lettori senza licenza](https://confluence.atlassian.com/spaces/CONFKB/pages/1381400731/Methods+to+allow+unlicensed+users+to+read+Confluence+Cloud+content) di Atlassian; Atlassian segnala quell'articolo come da correggere, la ricerca consiglia di ricontrollarlo, e un'affermazione di terze parti secondo cui l'accesso anonimo termina dopo il 1 dicembre 2026 non è confermata.
- Negativo, perché è il servizio di Atlassian, quindi il confronto gli assegna il punteggio, per definizione e non in base a un fatto emerso dalla ricerca, come non sull'infrastruttura propria dell'organizzazione e non leggibile senza accesso a Internet.
- Aperto: il contenuto tradotto (due file di ricerca sono in disaccordo sul fatto che l'articolo di Atlassian sulla traduzione del contenuto delle pagine copra Cloud, e una richiesta per Cloud di [versioni delle pagine per lingua](https://jira.atlassian.com/browse/CONFCLOUD-64788) è irrisolta), se Cloud attribuisca più autori di modifiche dentro una stessa versione, i controlli automatici, i diagrammi, i componenti interattivi.

### SharePoint Online (pagine e raccolte documenti)

- Negativo, perché ogni pagina di traduzione è aggiornata a mano, e, essendo il servizio di Microsoft, il confronto gli assegna il punteggio, per definizione e non in base a un fatto emerso dalla ricerca, come non sull'infrastruttura propria dell'organizzazione e non leggibile senza accesso a Internet.
- Aperto: un indirizzo separato per lingua, i controlli automatici sui link o sulla struttura, i componenti interattivi, i diagrammi, la licenza di cui hanno bisogno i lettori interni, la licenza per i flussi di approvazione delle pagine, la licenza per la revisione per l'eliminazione di Purview, e come il contenuto esce dalla piattaforma.

## Ulteriori informazioni

- Capitolo che questo registro sostiene: [Documentazione come codice](../00-foundations/docs-as-code.mdx).
- Registri correlati: ancora nessuno. Un successivo capitolo sull'hosting, con un proprio registro della decisione, copre l'accesso dei lettori, i limiti e le alternative per il sito pubblicato.
- Considerate e senza punteggio: Confluence Data Center (i nuovi clienti, cioè le organizzazioni che non hanno mai avuto posti utente Data Center a pagamento, [non possono acquistarlo dal 30 marzo 2026](https://www.atlassian.com/licensing/data-center-end-of-life), i clienti esistenti possono acquistare fino al 30 marzo 2028, e diventa di sola lettura il 28 marzo 2029; non è stabilito se questa organizzazione abbia mai avuto tali posti utente); il wiki provisioned di Azure DevOps, il wiki di GitLab e il wiki di GitHub (la ricerca copre chi può leggerli e modificarli e quale markup accettano, nulla sulle due lingue né sui controlli automatici); Markdown semplice in una forge autogestita come GitLab o Forgejo (la stessa forma del Markdown renderizzato da GitHub, che riceve il punteggio una volta sola, sulla forge decisa; ciò che una forge autogestita cambia è nelle condizioni di revisione qui sotto); Markdown semplice costruito da GitHub Pages con Jekyll (la documentazione di GitHub indica [Jekyll 3.10.0](https://pages.github.com/versions/) e un elenco fisso di plugin, e non menziona più lingue, il controllo dei link durante la build o i componenti JavaScript; la documentazione propria di Jekyll non è stata oggetto di ricerca); Azure DevOps Server (nessuna ricerca sulla pubblicazione di code wiki lì); Zensical (supporto per lingue e versionamento non stabilito); docfx (una sola fonte secondaria); Wiki.js (nessuna fonte leggibile).

Rivedi questa decisione quando si verifica una di queste condizioni:

- La maggior parte degli autori non usa git e non aprirà pull request: tieni il sito e aggiungi uno strumento di traduzione self-hosted come [Weblate](https://docs.weblate.org/en/latest/formats.html), il cui supporto per MDX non è nella ricerca, oppure, se la revisione di ogni modifica in git non è richiesta, passa a una piattaforma modificata nel browser, dove i controlli basati su file di questo repository non si applicherebbero.
- Servono più di due lingue, oppure traduttori esterni: sposta la traduzione dai timbri con hash a uno strumento di gestione delle traduzioni. Nessun riscontro della ricerca fissa quella soglia; è un giudizio dell'autore e non è verificata.
- Il contenuto è in una sola lingua e sono poche pagine per ingegneri che hanno tutti accesso al repository, senza componenti interattivi: Markdown renderizzato da GitHub basta.
- La forge è autogestita, oppure le linee guida devono essere servite dall'infrastruttura propria dell'organizzazione (questo ribalta la decisione sulla forge, sull'host o su entrambi): tieni Docusaurus, il cui output è fatto di file statici che un altro host può servire, e assegna di nuovo il punteggio a revisione, controlli che fermano un merge, raggiungibilità, continuità e infrastruttura propria per quella forge e quell'host. Su un GitLab autogestito, le approvazioni che bloccano un merge richiedono il [tier Premium o Ultimate](https://docs.gitlab.com/user/project/merge_requests/approvals/), "Pipelines must succeed" è un'[impostazione di progetto](https://docs.gitlab.com/user/project/merge_requests/auto_merge/) in ogni tier, [GitLab Pages](https://docs.gitlab.com/user/project/pages/) è nel tier Free, e il suo [controllo degli accessi](https://docs.gitlab.com/user/project/pages/pages_access_control/) offre "Only Project Members" o "Everyone" in ogni tier. Su Forgejo, la protezione dei branch può richiedere [un numero di approvazioni](https://forgejo.org/docs/latest/user/protection/); i controlli di stato obbligatori non sono menzionati nella documentazione propria di Forgejo.
- L'organizzazione lascia GitHub Enterprise Cloud, oppure passa a GitHub Enterprise Cloud con data residency: la pubblicazione privata su GitHub Pages dipende da Enterprise Cloud, e Pages non è menzionato nell'elenco delle funzionalità per la data residency; decidi di nuovo l'host.
- La documentazione è assemblata da molti repository e più versioni di prodotto devono essere pubblicate fianco a fianco, in una sola lingua: Antora.
- Un selettore di versione pubblicato diventa un requisito (questo ribalta la decisione sul versionamento): abilita il versionamento dei docs di Docusaurus, tieni meno di 10 versioni, e metti a budget una copia tradotta per versione, la cui struttura delle cartelle non è verificata.
- L'organizzazione sposta la propria documentazione su Azure DevOps (questo ribalta la decisione sulla forge), ogni lettore ha l'accesso Basic, e non servono né componenti interattivi né immagini SVG: il code wiki di Azure DevOps in un progetto privato, con le branch policy come unico gate.
- La versione 4 di Docusaurus rompe i componenti del sito oppure il progetto smette di rilasciare: riesamina le alternative qui sopra, partendo dai punti aperti elencati per ciascuna.
- Un parco esistente di Material for MkDocs: pianificane il passaggio a Zensical prima del 5 maggio 2027; il supporto di Zensical per lingue e versionamento non è verificato.
- Gli stakeholder devono leggere senza un ruolo sul repository e il sito non può essere pubblico: la documentazione di GitHub non descrive alcun modo per farlo su GitHub Pages (con Enterprise Managed Users, non è documentato se un membro dell'enterprise senza accesso in lettura al repository possa aprire un sito), quindi è una questione di hosting per il capitolo sull'hosting.
- Il capitolo sull'hosting sceglie un host diverso da GitHub Pages: assegna di nuovo il punteggio a raggiungibilità, continuità e infrastruttura propria per i generatori su quell'host.
- La ricerca chiude punti aperti di Docusaurus o di un'alternativa: assegna di nuovo il punteggio; il confronto può allora separarli.
