# ADR 0002: Guideline governance in the repository, with owners, expiring exception records and a review cycle

## Context and Problem Statement

The guidelines live in this repository and change by pull request ([ADR 0001](/adr/0001-docs-as-code-with-docusaurus.md)); since 2026-11-14 the repository's checks also run on every pull request, where they report a result without stopping a merge. The repository is public and belongs to an organisation: on 2026-11-18 a read-only `gh api repos/massimilianolapuma/cloud-architect-devops`, run during the design of this record, returned visibility public and owner type `Organization`; the organisation's plan was not observed. On GitHub ["public repositories are accessible to everyone on the internet"](https://docs.github.com/en/enterprise-cloud@latest/repositories/creating-and-managing-repositories/about-repositories). Every chapter names an owner and a date of last review, and `task content:lint` requires both, but nothing yet says what an owner is accountable for, how a team that cannot follow a guideline asks for an exception, where that exception is recorded, when it ends, or how often a chapter must be reviewed. The guidelines cover Azure, Google Cloud and on-prem clusters, and the project specification already names a rule that admits a deviation only as an approved and recorded exception (point-in-time restore of a tenant's data). The question is where exceptions are requested and recorded, what makes them expire, how the owner of a guideline takes part in the decision, and what the review cycle is.

## Decision Drivers

The weights sum to 100; the decider set them on 2026-11-18.

- One register for every platform, and for rules that no policy engine enforces (15). The guidelines cover Azure, Google Cloud and on-prem; some rules are process rules.
- Expiry that cannot be skipped: a record without a valid expiry date is refused before the record is accepted, and lapsed records are reported on a schedule that nobody has to start (25). The brief asks when an exception expires.
- Evidence for an audit: who asked, who approved, when, why and what compensates, the approval recorded by the system itself, and the record kept after it lapses (20). The specification puts compliance and audit at the core.
- The owner of the guideline concerned is asked, an approval is required before the record is accepted, and the requester cannot approve his own request (15). The brief asks who owns each chapter.
- Cost to run and testable on a workstation: no new product, seat or cloud account (15). The specification requires everything to be provable locally; the Cloud Adoption Framework recommends a [small governance team](https://learn.microsoft.com/azure/cloud-adoption-framework/govern/build-cloud-governance-team).
- Exit cost: what can be taken out, in what form, and what must be rebuilt elsewhere (10). The specification's decisions include avoiding lock-in.

A property is credited only where a source documents it; a property that only an unverified point would support is not credited; a check or a review that is not required counts as not met; and every documented way to get around a property (a bypass, an administrator, a deletion, a status set by someone else, a run delayed, dropped or disabled) halves it, for every option alike. The drivers score the record; none of the options that keep a register controls when an exception takes effect on a platform.

## Considered Options

- Governance records in the guidelines repository
- Platform-native exemption objects as the register
- Governance body with GitHub Issues and Projects as the tracker
- Governance body with Azure Boards as the tracker
- Governance body with Jira Cloud as the tracker
- Decision records only

## Decision Outcome

Chosen option: "Governance records in the guidelines repository", because the decider chose it: an exception is not a decision about the guideline, it ends on a date while a decision record is superseded and never edited, and keeping the two apart keeps the decision log short. The alternatives were examined. As designed, the evidence separates all five of them from the chosen option; in every case, best cases included, it still separates three (platform-native objects, GitHub Issues and Projects, Azure Boards); it does not separate decision records with an expiry field, nor Jira Cloud with every open point resolved in its favour. That is stated here plainly and is not a reason to change the choice.

Each option is scored as designed, with the mechanisms its documentation describes, none of them exercised. On the six drivers the options total 390 (records in the repository), 320 (decision records only), 300 (Azure Boards), 295 (Jira Cloud), 260 (GitHub Issues and Projects) and 160 (platform-native objects). The totals compare; they do not rank. The levels, the reason for each score and the arithmetic are in the [chapter](/00-foundations/governance.md).

What the evidence shows, option by option, against the chosen option:

- Decision records only (320): separated on expiry, because a decision record has no expiry field, and on audit evidence, because requester, scope and compensating control are not parts of it. Not separated on one register, on the owner's approval (a `CODEOWNERS` line per chapter can match a naming convention inside the one folder of decision records as well as a folder per chapter), on cost or on exit. With an expiry field and the missing fields added to their contract, decision records total 390 and are not separated on any driver. The decider chooses separate records for the reason above, which is not scored.
- Jira Cloud (295): separated on expiry (whether a required field can be a date is not in the research), on audit evidence (what an approval records is not documented), on cost (a separate product, not testable locally) and on exit (a CSV export of at most 10,000 work items, a backup that does not say whether it includes history). Not separated on one register or on the owner's approval, where its approval step can exclude the reporter. With every open point resolved in its favour and the product already licensed, it totals 390 and is not separated: one level ahead on expiry, one level behind on cost and on exit.
- Azure Boards (300): separated on audit evidence and the owner's approval (a permission saves work items without rule evaluation; the approvers are a fixed group; no rule against self-approval is documented), on cost and on exit. Not separated on one register or on expiry. With its open points resolved it totals 355 and stays separated on audit evidence, the owner's approval, cost and exit.
- GitHub Issues and Projects (260): separated on every driver but one register: forms have no date element, issues have no approval step, the records live outside git and the export is limited.
- Platform-native objects (160): separated on every driver. Not scored, and in their favour: the record is the enforcement, so the two cannot drift, and on some platforms the exception ends by itself at its date.
- What the chosen option's scores rest on: forge rules that the delivery phase wires. Without them, as the repository will stand when the chapter is written and also after the follow-up work of phase 0, the chosen option totals 280, and so do decision records only, whose credited review needs the same forge rules: the two are not separated. Only Azure Boards (300) and Jira Cloud (295) configured as designed score above them, each a separate product.
- The weights move only the order of Azure Boards and Jira Cloud: with the weights of the earlier draft (no exit-cost driver) or with equal weights, every separation above holds.

Decided by the decider on 2026-11-18, and recorded here as decided:

- **Exceptions are records of their own, not decision records.** The reason is the one given above.
- **Owner.** Each chapter has one owner, named in its frontmatter. Microsoft Learn defines the owner of an article as the one ["responsible for decisions about the content"](https://learn.microsoft.com/contribute/content/metadata); Google's engineering book says ["Documents without owners become stale"](https://abseil.io/resources/swe-book/html/ch10.html); Backstage's catalog says ["There will always be one ultimate owner"](https://backstage.io/docs/features/software-catalog/descriptor-format/). The owner decides the content, reviews the chapter on schedule and decides exceptions to it. The deciders of the chapter's decision record are the escalation point, as the executive sponsor is in the [Cloud Adoption Framework](https://learn.microsoft.com/azure/cloud-adoption-framework/govern/build-cloud-governance-team), and they name a new owner when one leaves.
- **A deputy.** A second person with write access approves the exceptions the owner requests for his own chapters, because on GitHub ["Pull request authors cannot approve their own pull requests"](https://docs.github.com/en/enterprise-cloud@latest/pull-requests/collaborating-with-pull-requests/reviewing-changes-in-pull-requests/approving-a-pull-request-with-required-reviews). The deputy is named when the forge rules are wired, in the delivery phase. Until then the chapter states that self-approval is not possible and what happens meanwhile.
- **Record and expiry.** One file per exception under `website/docs/exceptions/SECTION/CHAPTER/`, where `SECTION/CHAPTER` is the path of the chapter whose rule is relaxed, published with the guidelines, with its own document type and an Italian translation. Its expiry date is mandatory, at most 6 months after approval. One renewal is decided by the owner; a second goes to the deciders and triggers a review of the rule. A warning starts 30 days before expiry. A record whose date has passed is expired without anyone editing it, and it stays in the repository: Azure keeps an expired exemption ["for record-keeping, but the exemption is no longer honored"](https://learn.microsoft.com/azure/governance/policy/concepts/exemption-structure). A renewal is a new record that names the one it replaces. A record's status is one of proposed, approved, rejected, withdrawn, closed and replaced; expired is read from the date.
- **Review cycle.** Every chapter is reviewed at least every 6 months, and earlier when an event occurs: a minor release, an end of life or an API removal on a platform the chapter names; an incident or a failed control traced to the guideline; a change in regulation; a second active exception to the same rule, a trigger the decider set; a revisit condition of the chapter's decision record becoming true. The Cloud Adoption Framework recommends [scheduled reviews together with event-based ones](https://learn.microsoft.com/azure/cloud-adoption-framework/govern/document-cloud-governance-policies); the documented intervals run from a reminder after [three months](https://abseil.io/resources/swe-book/html/ch10.html) through [every four months](https://learn.microsoft.com/azure/well-architected/design-guides/implementing-recommendations) to [quarterly, biannually or yearly](https://learn.microsoft.com/azure/cloud-adoption-framework/govern/assess-cloud-risks).
- **Public by default; detail that may not be public goes to a private repository.** Everything added to this repository is public from the moment it is pushed: the record, the pull request that adds it, its commits, comments and review, the issue the dated report opens and the logs of its workflow, whether or not the site renders them, and a file removed later stays in the git history. A record therefore holds only what may be public: the rule, the category, the dates, the names of requester and approver, a scope written as a class of system, the reason and the compensating control at the level of the guideline, and the kind of each platform object with the generic steps to remove it. Names or identifiers of systems, tenants, customers and resources, ticket references, evidence and the commands that list platform objects go to a private repository of the same organisation, one file per record under the same identifier.
- **Wording of rules.** Chapters mark rules "must" or "should" from now on, as the Cloud Adoption Framework writes policy statements [in that language](https://learn.microsoft.com/azure/cloud-adoption-framework/govern/document-cloud-governance-policies); an exception is needed for a "must" or "must not". Stable rule identifiers are decided with the first chapter that states rules.
- **Timing of the follow-up work.** Now: the exception document type in the content lint with its templates, the dated report as a task, a `CODEOWNERS` file and the owner's GitHub handle in each chapter with a check between the two. In the delivery phase, with the other forge enforcement: the scheduled workflow of the report and the rulesets.
- **No tracker** is used for exceptions, and the chapter has one static diagram of the life of an exception.

Proposed by the author inside those decisions, and approved or changed with the design of this topic:

- **Rulesets on the forge.** The code owner's review required by a ruleset, with stale approvals dismissed, so that a change pushed after an approval needs a new one: the approving review ["is dismissed as stale, and the pull request cannot be merged until someone approves the work again"](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets). The job of the gates a required status check in a ruleset with no bypass actor, with the app that sets its status pinned as its source, so that ["If the status is set by any other person or integration, merging won't be allowed"](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets); whether GitHub Actions can be pinned as that source is not in the research. Rulesets rather than classic branch protection because a ruleset bypass can be limited to ["For pull requests only"](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/creating-rulesets-for-a-repository), so that the owner's own changes still go through a pull request, while the bypass list of branch protection skips the pull request. Ruleset bypass actors are roles, teams and apps, not individual users, so the owner's bypass goes to a team of which he is the only member, and every member of that team bypasses. The team's membership is changed in the organisation's settings, not by a pull request, so no review in this repository covers it and whoever can manage the team can widen the bypass; who can do so and what trail it leaves is not in the research. Adding a member only after a reviewed pull request is a written rule that nothing enforces, and each review of a chapter checks that the owner is still the only member. Where the plan offers it, a path-based reviewer rule with no bypass requires the deputy's approval on the owner's own exception requests.
- **Until the deputy is named.** An exception the owner requests for his own chapter is merged by him without an independent approval; its record names him as requester and approver; the dated report lists every such record still active; and the deputy, once named, confirms or closes each one.
- **The run of the dated report by hand: at least every 28 days,** on the same weekday every four weeks. A monthly run was considered first; runs in consecutive calendar months can be up to 61 days apart, longer than the 30-day warning window, so a lapse could go unseen. The decider chose 28 days on 2026-11-18.
- **The order of approval.** The approver first pushes the commit that records the decision and then approves; with stale approvals dismissed, any later push needs a new approval.

What depends on the organisation's plan, which was not observed: the required review and the required status check are available for a public repository on every plan ([code owners](https://raw.githubusercontent.com/github/docs/main/data/reusables/gated-features/code-owners.md), [rulesets](https://raw.githubusercontent.com/github/docs/main/data/reusables/gated-features/repo-rules.md)). Bypass lists and the path-based reviewer rule need a repository that belongs to an organisation, which this one does; that is a necessary condition, and on which plans they, the mode "For pull requests only" and the list of bypasses in the [rule insights](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/managing-rulesets-for-a-repository) exist is documented only on GitHub Enterprise Cloud pages. If the plan lacks the bypass mode, the deputy is put on every `CODEOWNERS` line and no bypass is needed.

Not in place on 2026-11-18: no check reads an expiry date or compares a review date with today's date; the gates run on every pull request and report a result, but no rule requires them or any review before a merge; the repository has no `CODEOWNERS` file; one person is owner, decider and approver of every document, and no deputy is named.

### Consequences

- Good, because one record format serves exceptions to rules enforced on Azure, on Google Cloud and on a cluster, and to process rules that no engine enforces.
- Good, because the request reuses what ADR 0001 already provides (files, pull requests, gates) and needs no new product, seat or cloud account; the checks run offline with the repository's own tools.
- Good, because a lapsed record stays in the repository with its git history, and the approving review is kept by the forge with its author, state, time and the commit it applies to ([pull request reviews](https://docs.github.com/en/enterprise-cloud@latest/rest/pulls/reviews)).
- Good, because the records and their history leave with the repository as plain files, and the approver and approval date typed into each record leave with them.
- Good, because exceptions stay out of the decision log, which keeps recording decisions that last.
- Bad, because nothing enforces the expiry date, the review interval or the owner's review until the forge rules of the delivery phase are wired; until then the lint and the report show problems without stopping anything, and the dates are checked by hand at each review.
- Bad, because the required check can be satisfied by a status of the same name set by another person or integration until an app is pinned as its source, and whether GitHub Actions can be pinned is not in the research.
- Bad, because the repository is public: a record cannot hold detail that may not be public, so for some exceptions the reason, the compensating control or the platform identifiers are kept in a private repository, with its own access control and its own trail; and a permitted record still tells an outsider which rule is waived until when, and who asked.
- Bad, because the pull request is public too: its commits carry the identity of their authors, anyone who can read the repository can comment in it, and a detail once pushed stays in the git history unless the history is rewritten. Contributors commit with an identity they accept to publish, and the reviewer checks the pull request text against the same list as the record.
- Bad, because the approval itself is a review on the forge, not a commit: on leaving GitHub it has to be read out through the forge's API before it is lost, and the enforcement (`CODEOWNERS`, rulesets and their bypass trail) has to be rebuilt; an exported ruleset [leaves out its bypass list](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/managing-rulesets-for-a-repository).
- Bad, because the record does not control when an exception takes effect on a platform, and the record and the platform object can drift apart. No expiry is documented on the pages read for the Kyverno exception object ([Kyverno](https://kyverno.io/docs/exceptions/)), for Gatekeeper namespace exemptions ([Gatekeeper](https://open-policy-agent.github.io/gatekeeper/website/docs/exempt-namespaces/)) or for Organization Policy overrides ([Organization Policy](https://docs.cloud.google.com/organization-policy/overview)); Pod Security Admission exemptions are [statically configured](https://kubernetes.io/docs/concepts/security/pod-security-admission/); and Policy Controller leaves the [`admission.gatekeeper.sh/ignore` label](https://docs.cloud.google.com/kubernetes-engine/policy-controller/docs/how-to/policy-controller-exclude-namespaces) on a namespace removed from its exempt list. Each review compares the records with the platform's own report of what is exempt.
- Bad, because `CODEOWNERS` fails open: an invalid line is skipped and an owner without explicit write access [is not assigned](https://docs.github.com/en/enterprise-cloud@latest/repositories/managing-your-repositorys-settings-and-features/customizing-your-repository/about-code-owners), so a chapter can silently lose its required reviewer; and any one of several code owners is enough, so the deputy can also approve requests by others in the owner's place.
- Bad, because the scheduled report is best effort: GitHub may [delay or drop](https://docs.github.com/en/enterprise-cloud@latest/actions/reference/workflows-and-actions/events-that-trigger-workflows) scheduled runs under load, and because this repository is public it [switches scheduled workflows off](https://docs.github.com/en/enterprise-cloud@latest/actions/how-tos/manage-workflow-runs/disable-and-enable-workflows) after 60 days with no repository activity, which the page does not define. During a quiet period, and until the scheduled workflow exists, the report runs only when someone runs it by hand.
- Bad, because until the deputy is named the owner's own exceptions have no independent approval, and afterwards the owner's bypass for his chapter edits also lets him skip the deputy wherever the plan lacks the path-based reviewer rule; such a merge is a trail, not an approval.
- Bad, because part of the arrangement and the longer trails depend on what the organisation has, which was not observed: the ruleset options above are documented only for GitHub Enterprise Cloud, the rule insights dashboard needs GitHub Team or Enterprise Cloud, and the [enterprise audit log](https://docs.github.com/en/enterprise-cloud@latest/admin/monitoring-activity-in-your-enterprise/reviewing-audit-logs-for-your-enterprise/about-the-audit-log-for-your-enterprise), which keeps events for 180 days unless they are streamed, exists only for an enterprise.
- Bad, because a requester needs git and a pull request; the [docs-as-code chapter](/00-foundations/docs-as-code.mdx) lists the same limit for contributors.
- Bad, because every record published under `website/docs/` needs an Italian translation to pass `task i18n:check`, and until the content lint knows an exception document type no such record can be added without failing it.

### Confirmation

- Today, `task content:lint` fails a chapter that has no `owner` or no valid `last_reviewed` date, a decision record that has no `deciders`, and any document whose type it does not know (`tools/content-lint.mjs`). It runs on a workstation and, through `.github/workflows/verify.yml`, on every pull request, where it reports a result without stopping a merge. It checks that an owner is present, not who it is, and it compares no date with today's date.
- Planned for phase 0 and not built: the exception document type and a lint rule for its records (every field present, real dates, expiry within the maximum, the folder matching the guideline, the private reference an identifier and not a URL, the owner's handle matching its `CODEOWNERS` line, compared offline in the two files) inside `task content:lint`; the errors GitHub reports for `CODEOWNERS` are read on the forge at each review, not by the lint; a dated report run as a task, listing exceptions lapsed or about to lapse, records approved by their own requester and chapters past their review interval; a `CODEOWNERS` file.
- Planned for the delivery phase and not built: the rulesets that require the gates and the code owner's review; a [scheduled workflow that opens an issue](https://docs.github.com/en/enterprise-cloud@latest/actions/tutorials/manage-your-work/schedule-issue-creation) with the report, holding only identifiers, chapters and dates.
- Until those exist, and afterwards whenever the scheduled workflow has been switched off: the person who reviews an exception request reads the record and the pull request against the list in the chapter, and the owner runs the dated report by hand at the interval above and goes through the open exceptions, their platform objects and the review dates at each review of a chapter, using the chapter's checklist.

## Pros and Cons of the Options

### Governance records in the guidelines repository

An exception is a file with fixed fields in a folder of the chapter it relaxes, requested and approved by pull request, with a mandatory expiry date; owners are named in each document and, on the forge, per chapter.

- Good, because the register is tied to no platform. Microsoft's own Azure Policy as Code layout keeps exemptions as [files in source control](https://learn.microsoft.com/azure/governance/policy/concepts/policy-as-code), next to the assignment they relax and deployed only after review.
- Good, because a mandatory date in a file can be read by an offline check written with the repository's tools, and that check can be made a [required status check](https://docs.github.com/en/enterprise-cloud@latest/repositories/configuring-branches-and-merges-in-your-repository/managing-rulesets/available-rules-for-rulesets).
- Good, because the code owner of the chapter is asked for review automatically and must approve, and the requester cannot approve his own pull request.
- Good, because the records leave as plain files with their history, and exceptions stay out of the decision log.
- Bad, because the lint rule, the report, the `CODEOWNERS` file and the forge rules do not exist yet.
- Bad, because administrators and bypass actors can merge without the owner's approval, a status of the same name can satisfy the required check until its source is pinned, and the scheduled report can be delayed, dropped or switched off after 60 quiet days.
- Bad, because the repository is public, so detail that may not be public lives elsewhere and a permitted record still discloses which rule is waived.
- Bad, because the platform object must be kept in step with the record by hand where the platform documents no expiry.
- Bad, because the enforcement is GitHub-specific and partly depends on the plan, and requesters need git; published records need translation.

### Platform-native exemption objects as the register

Each platform keeps its own record: Azure Policy and Defender for Cloud exemptions and attestations, Organization Policy overrides and tag conditions on Google Cloud, Kyverno, Gatekeeper, Kubewarden and Pod Security Admission on a cluster.

- Good, because the record and the enforcement are the same object, so they cannot drift.
- Good, because on Azure an exempt resource stays visible as [exempt](https://learn.microsoft.com/azure/governance/policy/concepts/exemption-structure), an exemption stops being honoured at its expiry date, and a rule checked only by hand can carry an [attestation](https://learn.microsoft.com/azure/governance/policy/concepts/attestation-structure) with an owner, evidence and an expiry.
- Bad, because each mechanism exempts only from its own engine, in its own format; outside Azure, a rule that no engine enforces has no object.
- Bad, because expiry is not guaranteed: `expiresOn` is [optional](https://learn.microsoft.com/azure/governance/policy/concepts/exemption-structure) on Azure Policy, only the Defender portal (in preview) makes it mandatory, and the pages read for [Organization Policy](https://docs.cloud.google.com/organization-policy/overview), Kyverno, Gatekeeper and Kubewarden document none on the exception itself (an absence, not a confirmed fact).
- Bad, because whoever holds rights on the platform grants the exception: on Google Cloud, whoever can attach the [tag](https://docs.cloud.google.com/resource-manager/docs/tags/tags-overview); on Azure, whoever holds the exemption permissions on the scope. The owner of the guideline is not part of the mechanism.
- Bad, because creating or reading the records on Azure and Google Cloud needs a real tenant or organisation for each platform, a cost for the organisation that keeps the register, and it cannot be tested on a workstation (this project's own local-first rule limits what the project tests, not where an adopting organisation keeps its register); on Google Cloud more than 20 [Policy Analyzer](https://docs.cloud.google.com/policy-intelligence/docs/analyze-organization-policies) queries a day need a paid tier; leaving means reading each platform separately.

### Governance body with GitHub Issues and Projects as the tracker

Requests are issues in this repository, decided by a named group; the issues are the register.

- Good, because it adds no product: the forge and its scheduled workflows already exist.
- Good, because a scheduled workflow can list issues whose date has passed ([scheduled issue creation](https://docs.github.com/en/enterprise-cloud@latest/actions/tutorials/manage-your-work/schedule-issue-creation)), and in this public repository a required field of an issue form [is enforced](https://docs.github.com/en/communities/using-templates-to-encourage-useful-issues-and-pull-requests/syntax-for-githubs-form-schema).
- Bad, because forms have no date element, organisation [issue fields](https://docs.github.com/en/enterprise-cloud@latest/issues/tracking-your-work-with-issues/using-issues/managing-issue-fields-in-your-organization) have a date type but are in public preview, and the register would be as public as the repository.
- Bad, because issues have no approval step: the research found the rule against approving one's own work for pull requests only.
- Bad, because organisation administrators can [delete an issue](https://docs.github.com/en/enterprise-cloud@latest/issues/tracking-your-work-with-issues/administering-issues/deleting-an-issue) permanently once deletion is enabled, without notifying collaborators, and contributors can edit their issues.
- Bad, because leaving is limited: a Projects view [exports as TSV](https://docs.github.com/en/enterprise-cloud@latest/issues/planning-and-tracking-with-projects/managing-your-project/exporting-your-projects-data), and a full [migration archive](https://docs.github.com/en/enterprise-cloud@latest/migrations/using-ghe-migrator/exporting-migration-data-from-githubcom) needs a preview API and is deleted after seven days.

### Governance body with Azure Boards as the tracker

Requests are work items of a custom type in Azure Boards (Azure DevOps Services), decided by an approvers group.

- Good, because a custom field can be [required](https://learn.microsoft.com/azure/devops/organizations/settings/work/add-custom-field?view=azure-devops) and rules are [enforced through the API too](https://learn.microsoft.com/en-us/azure/devops/organizations/settings/work/rule-reference?view=azure-devops); a transition to approved can be restricted to an [approvers group](https://learn.microsoft.com/azure/devops/release-notes/2020/sprint-172-update#azure-boards), stamped with the current user and time.
- Good, because every revision records [who, when and which fields changed](https://learn.microsoft.com/azure/devops/boards/queries/history-and-auditing?view=azure-devops), a deleted work item goes to a recycle bin as a new revision, and the records are not public: private projects [require sign-in](https://learn.microsoft.com/en-us/azure/devops/organizations/projects/about-projects?view=azure-devops).
- Good, because requesters can use free [Stakeholder access](https://learn.microsoft.com/en-us/azure/devops/organizations/security/stakeholder-access?view=azure-devops), and expiry can be reported by a [scheduled pipeline](https://learn.microsoft.com/azure/devops/pipelines/process/scheduled-triggers?view=azure-devops).
- Bad, because holders of one permission can save work items without the rules, which gets around the required fields and the approval transition, and a destroyed work item [cannot be restored](https://learn.microsoft.com/en-us/azure/devops/boards/backlogs/remove-delete-work-items?view=azure-devops).
- Bad, because the inherited process documents no rule that stops the requester from approving his own request, and whether a required field can be a date is not in the research.
- Bad, because it is a separate product outside the repository, not testable locally, and its organisation audit log is in preview, [off by default and kept 90 days](https://learn.microsoft.com/en-us/azure/devops/organizations/audit/azure-devops-auditing?view=azure-devops).
- Bad, because leaving costs a second step: a [CSV export](https://learn.microsoft.com/en-us/azure/devops/boards/queries/import-work-items-from-csv?view=azure-devops) holds current values only, the history needs the revision APIs, and moving a project to another organisation loses data.

### Governance body with Jira Cloud as the tracker

Requests are work items in a company-managed Jira Cloud space on a paid plan, decided through an approval step.

- Good, because fields can be made [required](https://support.atlassian.com/jira/kb/cant-create-issues-because-of-required-fields-in-jira-cloud/), an [approval step](https://support.atlassian.com/jira-software-cloud/docs/set-up-approval-steps/) takes its approvers from fields and can exclude the reporter, and a [scheduled automation](https://support.atlassian.com/jira-software-cloud/docs/automation-triggers/) can act on the work items a query returns.
- Good, because with every open point resolved in its favour and the product already licensed, the evidence does not separate it from the chosen option.
- Bad, because a scheduled flow that fails 10 times in a row switches itself off, and automation runs on a [monthly step allowance](https://support.atlassian.com/cloud-automation/docs/how-is-my-usage-calculated/), stopping at the limit unless extra usage is billed (from 2026-12-03).
- Bad, because deleted work items [cannot be recovered](https://support.atlassian.com/jira/kb/how-to-mass-delete-issues-in-jira/), and the [audit log](https://support.atlassian.com/jira-cloud-administration/docs/audit-activities-in-jira-applications/) is not available on the Free plan.
- Bad, because whether a required field can be a date, what an approval step records about each approver, and on which plans approval steps exist are not in the research.
- Bad, because it is a separate product outside the repository, not testable locally, and the self-hosted Data Center edition is [no longer sold to new customers](https://www.atlassian.com/licensing/data-center-end-of-life).
- Bad, because leaving is limited: a [CSV export](https://support.atlassian.com/jira/kb/export-over-10-000-work-items-in-jira-cloud/) holds at most 10,000 work items, and the [backup](https://support.atlassian.com/jira-cloud-administration/docs/export-issues/) excludes automation and does not say whether it includes change history.

### Decision records only

Every exception is a decision record in the existing `adr/` folder, with the existing contract, named per chapter so that a `CODEOWNERS` line per chapter can match it.

- Good, because nothing new is needed but forge settings and a naming convention: the template, the lint rule and the pull request exist.
- Good, because the log is version controlled, as the [Well-Architected Framework](https://learn.microsoft.com/azure/well-architected/architect-role/architecture-decision-record) recommends for decisions, and it leaves with the repository as plain files.
- Good, because with an expiry field and the missing fields added to the contract, the evidence does not separate it from the chosen option.
- Bad, because the contract has no expiry field, so no check can read one, and no field for requester, scope or compensating control; adding them changes what a decision record is.
- Bad, because an accepted record is not edited and is superseded by a new one, while an exception ends on a date: the two lifecycles do not match.
- Bad, because time-limited exceptions would fill the log that records lasting decisions, and the log is public like the rest of the repository.
